## 0. 一句话策略

**主打"时序融合净收益 +4.29（BEST）/ +3.74（窗口），四类全涨、13/13 epoch 领先"，用机制消融
证明"必须是 RSSM 这种带随机建模的结构"；同时主动交代"RSSM vs GRU 在最终栈上还没出数"，
把 GRU 控制列为进行中。**

关键认知：明天的证据能证明的是 **①时序融合有用、②RSSM 的内部设计每一项都贡献**；
它**还不能**证明 **③RSSM 比 GRU 好**。②③是两件事，老师大概率会追问③——所以要主动先说，
而不是等着被问。抢先把③说成"正在补的对照"，汇报的可信度会明显不同。

## 2. 页面顺序（建议 7 页）

**P1 结论先行**：一页给三个数 —— 时序融合净收益 **+4.29 BEST / +3.74 窗口**、四类全部同向、
ep12-24 **13/13** 个 epoch 领先。先给结论，后面才是证据。

**P2 对照为什么是干净的**（这页必须有）：贴 config diff，证明两份配置差别只有
`temporal_fusion: None ↔ MotionAlignedRSSMFusion`（其余是 `work_dir`/`figures_path`/checkpoint
interval/KL-scheduler hook 等记账项，在 `temporal_fusion=None` 下不生效）。
没有这页，老师第一反应会是"你这两次跑是不是还改了别的"。

**P3 不是挑峰值**：贴逐 epoch 差距表（ep12-24 全为正，均值 +3.17，最小 +1.74）。
把"最小 +1.74 仍然为正"这句话讲出来，比讲峰值 +4.77 有用。

**P4 不是拆东墙补西墙**：贴逐类拆解。四类全是正的（Cyc +8.58 / Truck +4.90 / Car +2.11 /
Ped +1.57），证明不是拿某一类的分换另一类。

**P5 稳定可复现**：RSSM 三 seed 39.88 / 40.51 / 40.88（40.42±0.51），峰值落在 ep16/15/14。
可补一句：单帧那一侧只有 seed0 一次，所以主对比是 seed0 对 seed0。

**P6 为什么必须是 RSSM**：机制消融表。删随机性 −1.44、固定噪声 −1.46、删 prior −0.22；
KL=0 单点看似 +0.47 但三 seed 翻负（−1.05）。结论：确定性传播与随机建模两条腿都必需，
单独抽掉任何一条都掉 1.3~2.0。

**P7 进行中的对照 + 计划**（主动交代）：GRU 控制 run 已配置好、启动过两次、均因 GPU 争用被杀；
等方法 run 释放 3 卡（明天约 11:00）后重跑，约需 19–21 h。同时给方法 run 自己的进度。

## 4. 必须避开的坑

1. **别把 18e 的数（Run 1 GRU 34.50 *、Run 5 RSSM 33.77）和 24e 的数放同一栏**——栈不同
   （无预训练 / head-v1 / 18e），跨栏相减会得出完全错误的结论。
2. **绝不要用 35.59 − 34.50 = 1.09 当"时序融合的效果"**。这两个数来自两个栈：单帧那份
   多出预训练（+3.23）与 head-v2（≈+2），同时去掉时序融合（−4.29），三项近似抵消。
   真实值是表 1 的 **+4.29**。
3. **别把 +4.29 说成"RSSM 比 GRU 好 +4.29"**。它是"时序融合 on/off"，不是"RSSM vs GRU"。
   这么讲会被一句"那随便加个 GRU 呢"问倒。
4. **别引用 KL=0 的 40.35 单点**（表 4 最后一行已说明它多 seed 翻负）；也别引用全库最高的
   41.10（那是 KL=0 seed1 的单点，不可信）。
5. **别把 fgfull 的 40.69 或任何 FG 栈的数当自己的成绩**——那一栈一次多了十余个变量
   （2D instance、IGDR、msk2d、rangeview、FRPN…）。
6. **18e 那一段如果要讲，只讲归因**：当时 RSSM 输给 GRU（33.77 vs 34.50）的原因是
   `output_proj` 零初始化 + `kl_scale=0.1/free_nats=0` 把 KL 压死（诊断见 §8.1），
   属**配置问题**而非结构问题；修复（Xavier + `action_dim=0`）之后的 24e 栈才拉开差距。
   诚实的说法是"早期栈下 RSSM 还没调好"，而不是"早期栈证明了 RSSM 不行"。

## 5. 预判提问与回答

**Q：你这 +4.29 是相对"没有时序"。我加个最简单的 GRU 是不是也差不多？**
A：这正是我目前在补的对照。18e 时代 GRU 是 34.50、RSSM 33.77，但那一代 RSSM 有配置问题
（output_proj 零初始化 + KL 压死）。最终栈上的 GRU 控制 run 已经配好（与我的方法 run 只差
`temporal_fusion` 一个变量），前两次启动都被 GPU 争用杀掉了，等方法 run 释放卡就重跑，约 20 小时。
**在这个数出来之前，我不会说 RSSM 一定优于 GRU。**

**Q：会不会只是峰值挑得好？**
A：不是。ep12–24 十三个 epoch 全部领先，平均 +3.17，最小值也有 +1.74；三 seed 峰值分别落在
ep16/ep15/ep14。

**Q：会不会是牺牲某一类换 Overall？**
A：四类全部同向提升，没有一类下降。

**Q：为什么不用确定性传播就够？（RSSM 的随机项有什么用）**
A：删随机性 −1.44、固定噪声 −1.46、删 prior −0.22；而关掉 KL 的单点收益在多 seed 下翻转成 −1.05。
说明确定性传播解释大部分但**不全部**，随机建模不可省。

**Q：瓶颈在哪？**
A：Pedestrian strict 长期 ≈0（三 seed 都 0.10–0.15），说明瓶颈在检测头/BEV 分辨率而非时序融合
——这条可以主动讲，显示对问题边界的判断。
